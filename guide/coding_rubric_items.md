# Code-quality rubric per case (C6 / C7 / C8 / C9)

Pass/fail is unchanged (the source benchmark's hidden tests). Code quality is graded by one LLM judge (Claude Opus 5.5) on the 3 common items below plus each case's 1–2 items. Levels: perfect 1.0 / accept 0.6 / bad 0; quality = 100 × mean.

## Common items (every case; meanings from C3 D3–D5)

| Item | 评分项 | Question | Perfect | Accept | Bad | Caps |
|---|---|---|---|---|---|---|
| READABILITY | 可读性 | Is the agent's code easy to read: intent-revealing names, formatting consistent with the existing code, docstrings/comments where logic is non-obvious? | Intent-revealing naming that reads like natural language; formatting consistent with the existing codebase; public interfaces documented; complex logic has inline comments (minor documentation gaps on non-obvious logic are still perfect). | Mostly readable, but some cryptic names (temp, data1, v) or complex logic without comments. | Inconsistent naming/casing, large undocumented blocks, confusing layout, or cryptic naming throughout. | Single-letter variable names in business logic (not loop counters) -> at most accept. |
| MAINTAINABILITY | 可维护性 | Is the change well structured and easy to change later: separation of concerns, short single-responsibility functions, reuse of existing helpers, no copy-pasted logic, no dead code / debug leftovers? | Clear separation of concerns; short single-responsibility functions (mostly < 30 lines); reuses existing helpers and patterns; loose coupling; no copy-pasted logic, dead code or debug output. | Standard structure, but some details leak across layers, a few functions are monolithic, there is some duplicated logic, or leftover dead code / debug output. | Monolithic functions (> 80 lines), high complexity or deep nesting (4+ levels), systemic copy-paste, global mutable state, or tight coupling. | A single new file > 500 lines -> at most accept. A single function > 100 lines -> bad. |
| ROBUSTNESS | 健壮性 | Is the code defensive: specific exceptions handled, resources managed safely, inputs validated at boundaries, no magic constants, errors never silently swallowed? | Defensive throughout: specific exceptions handled, safe resource management, input validation at boundaries, no (or < 2 minor) magic constants, concurrency-safe where relevant. | Errors are handled, but generic catch-all blocks are common, some magic constants, or 1-2 edge cases lack validation. | Errors silently swallowed (bare except / except Exception: pass), resource-leak risks, no input validation, or hardcoded credentials. | Bare except: / except Exception: pass in business logic -> at most accept. Errors silently swallowed on data-mutation paths -> bad. Hardcoded secrets/credentials -> bad. |
